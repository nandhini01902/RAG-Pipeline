# Medical PDF Question Answering (RAG)

A local Retrieval-Augmented Generation (RAG) demo for asking questions about
the medical-record PDF in `data/`. It extracts text page by page, indexes
section-aware chunks in local Qdrant, retrieves evidence with dense and sparse
search, and sends that evidence to Gemini to draft a cited answer.

> **Scope:** the checked-in corpus is one synthetic medical-record PDF. The
> project is not a clinical decision-support system and must not be used for
> diagnosis or treatment.

## Architecture

See the full [RAG pipeline flow diagram](RAG_PIPELINE_FLOW.md) for indexing,
question-time retrieval, answer generation, evidence-only inspection, and
evaluation paths.

## Workflow, step by step

### 1. PDF text extraction

[`src/text_extraction.py`](src/text_extraction.py) uses PyMuPDF to extract
each PDF page separately and preserve its original page number. It writes the
page records to `data/raw/extracted_text.txt`.

### 2. Text cleanup

[`src/clean_text.py`](src/clean_text.py) applies conservative whitespace,
punctuation, and known OCR-spacing repairs. It preserves clinical values,
records document IDs as metadata, and excludes page 16 because the data
quality review identifies it as a different patient's record. Cleaned records
and review notes are written to `data/processed/`.

### 3. Section-aware chunking

[`src/chunk.py`](src/chunk.py) identifies headings and paragraphs and uses
the `BAAI/bge-small-en-v1.5` tokenizer to split long passages. The current
configuration is **450 tokens per chunk with 80 tokens of overlap**. Each
chunk records its document ID, page, section, patient name when detected, and
text in `data/processed/chunks.json`.

[`src/chunk_text.py`](src/chunk_text.py) adds the section heading to the text
used for indexing. This allows section labels as well as the chunk body to
contribute to retrieval and generation context.

### 4. Embeddings and local vector index

- **Dense embeddings:** `BAAI/bge-small-en-v1.5`, generated by
  [`src/embedding.py`](src/embedding.py). Query vectors are normalized and
  use the model's retrieval query instruction; document vectors are
  normalized as well.
- **Sparse search:** local BM25-style term-frequency/inverse-document-
  frequency vectors, implemented in [`src/sparse_vectors.py`](src/sparse_vectors.py).
- **Vector store:** local Qdrant, in `outputs/qdrant/`. The index stores dense
  and sparse vectors with page, section, chunk, and patient metadata. At
  retrieval time, the chunk ID is joined to `chunks.json` to restore its
  document ID and original text.
- **Fusion:** Qdrant reciprocal-rank fusion (RRF) combines the dense and
  sparse candidate rankings.
- **Post-ranking:** a lightweight lexical reranker combines normalized RRF
  score (0.65), informative-token overlap (0.20), and section-token overlap
  (0.15). Patient-name matching affects ordering for patient-name searches.
  There are also domain-specific sparse query expansions for medication,
  imaging, restrictions, allergies, EMG, and lumbar-MRI questions, plus
  query-specific evidence limits.

To rebuild the local index after changing the source PDF or processing code,
run these commands from the repository root in order:

```powershell
.\.venv\Scripts\python.exe -m src.text_extraction
.\.venv\Scripts\python.exe -m src.clean_text
.\.venv\Scripts\python.exe -m src.chunk
.\.venv\Scripts\python.exe -m src.embedding
.\.venv\Scripts\python.exe -m src.vector_database
```

### 5. Answer generation

[`src/rag_pipeline.py`](src/rag_pipeline.py) packages each retrieved passage
with its document ID, original page number, section, and text. Gemini is
instructed to answer only from that evidence, distinguish conflicting
statements, avoid medical advice, cite claims as `[doc_id, page N]`, and reply
`I don't know.` when the evidence is insufficient. The Gemini key is read from
`.env`; keep that file private and use [`.env.example`](.env.example) as the
safe template.

Gemini quota errors do not fall back by retrying another model: fallback
models are only tried for temporary model-unavailable (`503`) errors. A
quota-exhausted project must wait for its reset or have its account quota
changed before generating answers.

### 6. Demo UI

[`app.py`](app.py) provides a Streamlit interface. **Generate answer** runs
retrieval and Gemini generation. **Inspect retrieved evidence (no Gemini
call)** performs retrieval only and displays the passages and the exact
prompt payload. Evidence inspection is useful when the Gemini free-tier
quota is exhausted.

Start the app from the repository root:

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py
```

Open the localhost URL printed by Streamlit (normally
`http://localhost:8501`).

## Evaluation

Run the retrieval-only evaluation; it does not call Gemini:

```powershell
.\.venv\Scripts\python.exe -m src.evaluate_retrieval
```

The runner evaluates unique-page rankings at `k = 1, 3, 5, 8, 10, 15` on a
10-question manually labeled benchmark. It calculates:

| Metric | Meaning |
|---|---|
| Hit Rate@k | Fraction of questions with at least one relevant page among the top k. |
| Recall@k | Relevant pages found among the top k divided by all labeled relevant pages. |
| Precision@k | Relevant pages found among the top k divided by k. |
| MRR@k | Mean reciprocal rank of the first relevant page, with misses scored zero. |
| nDCG@k | Normalized discounted cumulative gain using binary page relevance. |

Results are saved on each run to:

- `outputs/evaluation/retrieval_metrics.json` — timestamp, metric definitions,
  per-question relevant and ranked pages, per-question scores, and averages.
- `outputs/evaluation/retrieval_metrics.csv` — one aggregate row per k for
  experiment-table use.

High scores should not be generalized to arbitrary documents or questions.
