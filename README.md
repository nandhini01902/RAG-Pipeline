# Medical PDF Question Answering (RAG)

A local Retrieval-Augmented Generation (RAG) demo for asking questions about
the sample medical-record PDF or one or more PDFs uploaded in the Streamlit
app. Uploaded files are extracted and indexed together in a temporary,
in-memory Qdrant collection. The app retrieves evidence with dense and sparse
search and sends only the selected passages to Gemini to draft a cited
answer. For answer generation, Gemini first rewrites the question to correct
spelling and grammar while preserving the original intent; retrieval uses
that rewritten query, and answer generation still receives the original
question.

> **Scope:** the checked-in corpus is one synthetic medical-record PDF. The
> project is not a clinical decision-support system and must not be used for
> diagnosis or treatment.

For the detailed system and experiment write-up, see the
[project report](RAG_REPORT.md). This README remains the setup and usage guide.

## Workflow, step by step

### 1. PDF text extraction

[`src/text_extraction.py`](src/text_extraction.py) uses PyMuPDF to extract
each PDF page separately and preserve its original page number. It writes the
page records to `data/raw/extracted_text.txt`.

### 2. Text cleanup

[`src/clean_text.py`](src/clean_text.py) applies conservative whitespace,
punctuation, and known OCR-spacing repairs. It preserves clinical values,
records document IDs as metadata, and excludes page 16 because the data
quality review identifies it as a different patient's record. Cleaned records
and review notes are written to `data/processed/`.

### 3. Section-aware chunking

[`src/chunk.py`](src/chunk.py) identifies headings and paragraphs and uses
the `BAAI/bge-small-en-v1.5` tokenizer to split long passages. The current
configuration is **450 tokens per chunk with 80 tokens of overlap**. Each
chunk records its document ID, page, section, patient name when detected, and
text in `data/processed/chunks.json`.

[`src/chunk_text.py`](src/chunk_text.py) adds the section heading to the text
used for indexing. This allows section labels as well as the chunk body to
contribute to retrieval and generation context.

### 4. Embeddings and local vector index

- **Dense embeddings:** `BAAI/bge-small-en-v1.5`, generated by
  [`src/embedding.py`](src/embedding.py). Query vectors are normalized and
  use the model's retrieval query instruction; document vectors are
  normalized as well.
- **Sparse search:** local BM25-style term-frequency/inverse-document-
  frequency vectors, implemented in [`src/sparse_vectors.py`](src/sparse_vectors.py).
- **Vector store:** local Qdrant, in `outputs/qdrant/`. The index stores dense
  and sparse vectors with page, section, chunk, and patient metadata. At
  retrieval time, the chunk ID is joined to `chunks.json` to restore its
  document ID and original text.
- **Fusion:** Qdrant reciprocal-rank fusion (RRF) combines the dense and
  sparse candidate rankings.
- **Post-ranking:** a lightweight lexical reranker combines normalized RRF
  score (0.65), informative-token overlap (0.20), and section-token overlap
  (0.15). Patient-name matching affects ordering for patient-name searches.
  There are also domain-specific sparse query expansions for medication,
  imaging, restrictions, allergies, EMG, and lumbar-MRI questions, plus
  query-specific evidence limits.

### Upload and search your own PDFs

In the Streamlit app, select one or more PDFs in **Upload PDF documents**.
The app extracts page text, splits it into the same section-aware chunks, and
builds an in-memory dense+sparse Qdrant index for the selected documents.
Questions search across all selected PDFs, and each result retains its source
filename and page number. When no files are selected, the existing sample
corpus and its saved local Qdrant index are used.

Uploaded files are not added to the checked-in sample corpus or saved by the
app. Their index is recreated in memory when you request an answer or inspect
evidence. Scanned/image-only PDFs are not OCR-processed and must have
searchable text. **Generate answer** sends the rewritten question and
retrieved passages to Gemini; it does not send the full PDF. Do not upload
documents unless you are permitted to share their relevant excerpts with
Gemini.

To rebuild the local index after changing the source PDF or processing code,
run these commands from the repository root in order:

```powershell
.\.venv\Scripts\python.exe -m src.text_extraction
.\.venv\Scripts\python.exe -m src.clean_text
.\.venv\Scripts\python.exe -m src.chunk
.\.venv\Scripts\python.exe -m src.embedding
.\.venv\Scripts\python.exe -m src.vector_database
```

### 5. Query rewriting and answer generation

When **Generate answer** is selected, [`src/rag_pipeline.py`](src/rag_pipeline.py)
asks Gemini to correct spelling and grammar and produce a concise retrieval
query. The rewrite instruction requires it to preserve the user's intent,
names, dates, numbers, laterality, medical terms, and requested details; it
must not answer the question. The rewritten query is used for dense retrieval,
sparse retrieval, and reranking. The app displays the rewritten query.

The original question and rewritten search query are both included with the
retrieved evidence in the answer-generation request. Gemini is instructed to
answer the original question, using the rewritten query only as retrieval
context. Query rewriting is an LLM step and therefore makes a Gemini API
request before answer generation; quota or model errors are surfaced rather
than silently falling back to the original query.

**Inspect retrieved evidence** intentionally skips the LLM rewrite and uses
the original question so that evidence inspection remains a no-Gemini path.
The offline retrieval evaluation also uses its benchmark questions as written
and does not measure query-rewrite effectiveness.

### 6. Answer generation

[`src/rag_pipeline.py`](src/rag_pipeline.py) packages each retrieved passage
with its document ID, original page number, section, and text. Gemini is
instructed to answer only from that evidence, distinguish conflicting
statements, avoid medical advice, cite claims as `[doc_id, page N]`, and reply
`I don't know.` when the evidence is insufficient. The Gemini key is read from
`.env`; keep that file private and use [`.env.example`](.env.example) as the
safe template.

Gemini quota errors do not fall back by retrying another model: fallback
models are only tried for temporary model-unavailable (`503`) errors. A
quota-exhausted project must wait for its reset or have its account quota
changed before generating answers.

### 7. Demo UI

[`app.py`](app.py) provides a Streamlit interface. **Generate answer** runs
Gemini query rewriting, retrieval, and Gemini answer generation.
**Upload PDF documents** accepts multiple PDFs to search together; with no
uploads selected, the app uses the sample corpus. **Inspect retrieved
evidence (no Gemini call)** performs retrieval using the original question
and displays the passages and the prompt preview. Evidence inspection is
useful when the Gemini free-tier quota is exhausted.

Start the app from the repository root:

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py
```

Open the localhost URL printed by Streamlit (normally
`http://localhost:8501`).

### 8. Retrieval evaluation

Run the retrieval-only evaluation; it does not call Gemini:

```powershell
.\.venv\Scripts\python.exe -m src.evaluate_retrieval
```

The runner evaluates unique-page rankings at `k = 1, 3, 5, 8, 10, 15` on a
10-question manually labeled benchmark. It also compares two retrieval
configurations at fixed `k = 5`: Qdrant dense+sparse RRF alone versus the same
retrieval with lexical and patient-name reranking enabled. This isolates the
reranker as the only changed variable. Both experiments calculate:

| Metric | Meaning |
|---|---|
| Hit Rate@k | Fraction of questions with at least one relevant page among the top k. |
| Recall@k | Relevant pages found among the top k divided by all labeled relevant pages. |
| Precision@k | Relevant pages found among the top k divided by k. |
| MRR@k | Mean reciprocal rank of the first relevant page, with misses scored zero. |
| nDCG@k | Normalized discounted cumulative gain using binary page relevance. |

Results are saved on each run to:

- `outputs/evaluation/retrieval_metrics.json` — timestamp, metric definitions,
  per-question relevant and ranked pages, per-question scores, and averages.
- `outputs/evaluation/retrieval_metrics.csv` — one aggregate row per k for
  experiment-table use.
- `outputs/evaluation/configuration_comparison.csv` — aggregate scores for
  the two fixed-top-k reranker configurations.

### Chunking comparison

Run the chunking comparison separately:

```powershell
.\.venv\Scripts\python.exe -m src.evaluate_chunking
```

This compares the historical 34-chunk snapshot from commit `9d7535d` with
the current 68-chunk dataset. The older splitter separated paragraphs at
blank lines; the newer splitter also treats headings and selected metadata
labels as paragraph boundaries. Both datasets are re-embedded with
`BAAI/bge-small-en-v1.5` and evaluated with the same hybrid retrieval,
reranker, benchmark, and k values. Each configuration uses a temporary
isolated Qdrant index, leaving the active index unchanged.

The source-history version has **34 chunks** (the repository history contains
no 36-chunk snapshot); the current version has **68**. Average chunk length
changed from 352.8 to 157.4 tokens. On the same 10 questions at k=5:

| Chunk configuration | Hit Rate@5 | Recall@5 | Precision@5 | MRR@5 | nDCG@5 |
|---|---:|---:|---:|---:|---:|
| Earlier chunking (34 chunks) | 1.000 | 0.951 | 0.420 | 0.950 | 0.938 |
| Current chunking (68 chunks) | 1.000 | 0.957 | 0.420 | 1.000 | 0.987 |

At k=5, current chunking improves recall by 0.006, MRR by 0.050, and nDCG
by 0.049; hit rate and precision are unchanged. The full k sweep and
per-question rankings are saved in:

- `outputs/evaluation/chunking_comparison.csv`
- `outputs/evaluation/chunking_comparison.json`
- `outputs/evaluation/chunks_34_baseline.json` — frozen historical chunks so
  the comparison can be rerun without depending on Git history.

These are retrieval-only metrics on a small, single-document benchmark; they
do not establish statistical significance, answer quality, or clinical
safety.

### Reranker comparison (k = 5)

The local run compared the configurations on the same 10 questions, BGE
embedding model, hybrid RRF retrieval, and retrieval depth. Only lexical and
patient-name reranking changed:

| Configuration | Hit Rate@5 | Recall@5 | Precision@5 | MRR@5 | nDCG@5 |
|---|---:|---:|---:|---:|---:|
| RRF only | 1.000 | 0.937 | 0.400 | 1.000 | 0.960 |
| RRF + lexical reranker | 1.000 | 0.957 | 0.420 | 1.000 | 0.987 |

On this small benchmark, reranking improved recall by 0.020 and nDCG by
0.027, with hit rate and MRR unchanged. This is a retrieval-only result and
does not establish statistical significance or generated-answer quality.

|---|---|
| PDF extraction, cleanup, chunking, BGE embeddings, local vector database | Implemented for the sample PDF. |
| Page/document metadata and source citations | Page/document IDs are retained and provided to the prompt; output citation adherence is not automatically scored. |
| Retrieval metrics in section 6.1 | Implemented: Hit Rate@k, Recall@k, Precision@k, MRR@k, and nDCG@k. |
| Compare at least two configurations | Implemented: top-k sweep, fixed-top-k reranker ablation, and historical 34- versus current 68-chunk comparison. Parameter sweeps across additional chunk sizes or strategies are not yet implemented. |

| Query rewrite | Gemini-based query rewriting is implemented for answer generation; it preserves the original question and uses a rewritten query for retrieval. Rewrite quality is not separately evaluated. |

| Statistical analysis and final architecture/experiment report | The evaluation artifacts and this workflow README exist; confidence intervals, significance tests, effect sizes, and the final experimental report remain to be done. |
